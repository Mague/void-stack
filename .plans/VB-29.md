# VB-29 — Transporte HTTP streamable en void-stack-mcp

## Objetivo
Servir el mismo VoidStackMcp por HTTP (MCP streamable-http de rmcp) además
de stdio, para que clientes remotos (Claude Code en WSL, las Macs vía
Tailscale, el futuro dashboard) consuman el MCP sin reinstalar ni
re-registrar proyectos.

## Diseño
- Nuevo flag CLI en void-stack-mcp: `--http <addr>` (ej. `--http 0.0.0.0:7400`).
  Sin el flag, comportamiento actual intacto: stdio es el default.
- Usar el transporte streamable HTTP de rmcp (verificar el nombre exacto del
  módulo/feature en la versión de rmcp del Cargo.toml; actualizar la dep si
  la versión actual no lo incluye). El servicio VoidStackMcp NO cambia —
  solo el transporte en main.rs.
- main.rs: parsear el flag (clap, coherente con el estilo del daemon),
  branch stdio vs http. El logging a stderr se mantiene (en modo http ya no
  hay conflicto con stdout, pero no cambiar el comportamiento).
- Seguridad mínima: en modo http, loggear un warning si la addr no es
  loopback ni rango Tailscale (100.64.0.0/10) — el server no lleva auth,
  se asume tailnet/localhost de confianza.
- Modo dual opcional NO requerido: un proceso sirve stdio O http, no ambos.

## Fuera de alcance (no hacer)
- Auth/TLS propios (lo cubre Tailscale).
- Cambios en las herramientas o en el registro de proyectos.
- Registrar la URL http en setup.rs (será ticket aparte).

## Criterios de aceptación
1. `void-stack-mcp` sin flags → stdio, idéntico a hoy (los clientes
   actuales no notan nada).
2. `void-stack-mcp --http 127.0.0.1:7400` → un cliente MCP por HTTP lista
   las mismas herramientas que por stdio y semantic_search responde igual.
3. Desde WSL con networkingMode=mirrored: `claude mcp add --transport http
   void-stack http://localhost:7400` conecta y las herramientas ven los
   mismos proyectos registrados en Windows (%LOCALAPPDATA%).
4. cargo fmt --all --check, clippy -D warnings y cargo test --workspace
   en verde (pre-commit gate del proyecto).
5. Tests: unit test del parseo del flag + test de arranque http que haga
   al menos un initialize/list_tools contra el server levantado en puerto
   efímero.

## Notas
- Reusar patrones de CLI del daemon (clap ya está en el workspace).
- Si rmcp streamable-http requiere un runtime axum/hyper como feature,
  activarla solo en el crate void-stack-mcp, no en core.

## Notas de implementación (resultado)

- rmcp 1.1.0 ya trae el transporte: feature
  `transport-streamable-http-server`, tipos
  `rmcp::transport::streamable_http_server::{StreamableHttpService,
  StreamableHttpServerConfig, session::local::LocalSessionManager}`.
  No hubo que subir la versión de la dep.
- El servicio es un `tower::Service<http::Request<B>>`, así que necesita un
  runtime HTTP: se añade `axum` 0.7 (la misma versión que ya arrastra tonic
  en el lockfile) **solo** en `void-stack-mcp`.
- El router monta el servicio como `fallback_service`, de modo que
  `http://host:port/` y `http://host:port/mcp` apuntan al mismo endpoint
  (los clientes difieren en si añaden path).
- `--http` acepta `host:port`, `ip:port` y puerto suelto (`--http 7400` →
  `127.0.0.1:7400`); los nombres se resuelven con `ToSocketAddrs`.
- El aviso de bind no confiable vive en `cli::is_trusted_bind`: loopback,
  100.64.0.0/10 (CGNAT Tailscale) y fd7a:115c:a1e0::/48 (ULA Tailscale)
  son de confianza; cualquier otra cosa (incluido 0.0.0.0) loggea warning.
